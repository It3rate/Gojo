GojoCAD Read Algebra

GojoCAD structure is the source of meaning. A read algebra is an inspection surface generated from that structure at a chosen purpose, resolution, and time. It should make local discoveries easier to reuse without becoming a parallel model that owns the concept.

The read result should usually be a graph, not a strict tree. Gojo structures share carriers, locations, unit shapes, and TickRef sites, so the read must preserve shared evidence instead of duplicating it into unrelated branches.

GojoCAD relation graph
  canonical structure
  carriers, locations, relations, unit shapes, residue, tension

derived read graph
  temporary inspection surface
  local observations with links back to source structure
  ambiguity, partial detail, sampled choices, and unresolved residue

If a read becomes important enough to persist, it should crystallize back into ordinary Gojo structure as a witness relation. Until then, throwing away the read graph must not change what the structure means.

Recognition Direction

Recognition should be algebraic and bottom-up. Instead of testing every known shape at every relation, the reader should inspect the relation's left side, carry those findings into the right side, and narrow the possible reads by local compatibility.

For example:

Relation(left, right)
  read left
  read right
  combine compatible local findings
  carry resulting findings upward

The carried result can include several compatible reads. A relation of two coincident points can be an ordinary zero span, a line seed candidate, and a future orthogonal source. A parent relation may refine one of those readings without erasing the others.

Read Order And Bands

Order matters because higher reads depend on lower evidence. The reader should advance in bands, where each band can consume everything already carried and add more reads without erasing earlier possibilities.

The order should stay algebraic rather than becoming a giant classifier:

Band Current role Example reads
0 local primitive relation reads point, frame point, point pair, span, frame segment, zero span, directed segment, radial seed, circular marker/span
1 incidence, unit, and partition reads carrier unit/provenance, point attachment, shared site, segment partition, contour partition, segment connection
2 second-order control reads radius attachment, linear basis witness/alignment, segment join/flow/unit/junction, future perpendicular/equal-length witnesses
3 contour and curvature controls tangent continuity, curvature continuity, rounded corner, clothoid/involute witnesses
4 boundary, area, and topology controls closed boundary, boundary join/flow, area, anti-area, branch, merge, crossing/intersection
5 resolution and concept conditioning coarse-to-fine ladders, named concept hints, feature settlement witnesses

Bands 0, 1, 2, and the initial boundary/area reads in band 4 are executable right now. GraphicReadGraph.Bands exposes the non-empty read bands in order. The band number is a read-pass grade, not a symbolic shape tag; the source relation structure still carries the meaning.

Second-Order Control Reads

Second-order controls are not usually the visible primitive. They guide how visible primitives resolve: where a basis points, how far a radius reaches, which spans connect, whether a boundary closes, or which local ambiguity should remain as tension.

Useful families to preserve:

Family Control examples
incidence / attachment coincident points, point-on-segment, point-on-circumference, endpoint-to-endpoint, endpoint-to-contour point, branch node, merge node, intersection witness
direction / basis second point fixes a linear carrier, parallel carriers, anti-parallel carriers, perpendicular carriers, tangent-to-circumference, normal/radius alignment, angle relation, directed-flow alignment
metric equal length, proportional length, fixed radius, radius from attachment, equal radius, shared tick scale, partition ratio, circumference period, resolution ladder
contour / curvature arc span, tangent continuity, curvature continuity, clothoid transition witness, involute relation, spline control relation, corner, rounded-corner control, cusp/sharp-corner witness
area / boundary closed boundary, directed boundary, fill area, anti-area/cutout, inside/outside relation, winding direction, containment, shared boundary edge, area partition
topology / graph branch, merge, Y split, T junction, crossing without connection, crossing with connection, stroke order, path ordering, connected component witness
repetition / grade repeated partition, grid/lattice basis, symmetry, mirror, rotational symmetry, array along segment, array around circumference, low-to-high resolution read

These should be derived from relation evidence as far as possible. A future parallel read, for example, should be a relation between carrier bases or their witnesses; it should not be a stored Parallel enum. The current area read comes from closure plus fill participation: a closed boundary remains only a boundary until a fill carrier participates through an orthogonal boundary source. It does not start as an opaque polygon type.

Current join flow evidence is deliberately weaker than corner evidence. A two-endpoint join can share a carrier with opposed local flow, share a carrier with same-side local flow, or transition between carriers. A boundary read may later use that evidence to distinguish straight continuation, turn, cusp, rounding, or unresolved tension.

Branch and merge reads use directed endpoint flow before naming the topology. The lower read is PathJunctionRead: three or more path endpoints share a site. It becomes a branch only when all participating endpoints are directed and the local flow has exactly one incoming side with multiple outgoing sides. It becomes a merge only when the directed evidence reverses that count. Mixed or undirected junctions stay inspectable as unresolved junction topology.

Carrier unit evidence is deliberately weaker than kind-transfer evidence. Two joined carriers can share one unit identity, share compatible descriptor provenance through separate carrier instances, have the same bare algebra with different descriptors, or have different algebra altogether. This is the lower evidence needed before a future read can say "same path turned" or "one kind settled into another kind."

Polyline Basis Patterns

A polyline can be defined through at least two useful basis patterns.

The shared-frame pattern repeats data in one fused basis:

shared XY/group basis
point 0 -> x0, y0
point 1 -> x1, y1
point 2 -> x2, y2

Every point references the same coordinate surface. This is useful for global measurement, intersection, fill, projection, and direct editing.

The repeated-step pattern repeats a structural template:

step template
  start site
  local span / arc / radius / length evidence
  end site

step 0 instance
step 1 instance appended to step 0 end
step 2 instance appended to step 1 end

Each step can have its own carrier instance, direction, length, arc, or radius. The instances can still share template provenance through compatible UnitShape descriptors. This is repetition by addition: a new instance is appended to the current path, and route continuity comes from the ordered attachment of one step's end to the next step's start.

The stronger repeat-control foothold is now explicit:

input ports:   start, incoming basis, angle, length
selected:      relative angle/length step structure
output ports:  end, outgoing basis
feedback:      end -> next start, outgoing -> next incoming basis
controller:    repeat count / phase / later equation

The expanded geometry still gives ordinary connected segment, circular marker, radius, and linear witness reads. The repeat surface preserves the repeated template and feedback relation without turning the path into a code-side loop. Renderers should treat repeat-control surfaces as control evidence, not as ordinary visible controller geometry, until a dedicated repeat visualizer exists.

This distinction helps separate turn evidence from kind-transfer evidence:

turn
  route continuity
  carrier/basis transition
  compatible carried unit provenance

change of kind
  source-to-target transfer or settlement participation
  different unit descriptor provenance or algebra
  optional residue/tension from incomplete conversion

both
  route continuity plus transfer evidence

The same geometry can support more than one read. The read graph should carry both route and unit/provenance evidence upward rather than forcing a single label early.

The executable path layer now follows this split:

SharedFramePolylineRead
  emerges from ordered coordinate groups and frame segments
  all points refer back to the same coordinate carrier basis

OpenSegmentPathRead
  emerges from ordinary segment joins
  can read as a shared-carrier path or as repeated step instances when join
  unit compatibility carries shared template provenance

The repeated-step read is intentionally based on connected segment instances and their unit descriptors, not on a special polyline marker.

Evidence To Carry Upward

A useful read graph node should preserve enough local evidence for parent reads to narrow without rediscovering the entire subtree:

source element
recognized local reads
source carrier locations
shared TickRef sites
carrier face evidence
unit-shape evidence
child read links
attachments to neighboring reads
unresolved residue or tension-like missing detail
sampled values used by this read pass

The sampled values belong to the read pass, not to the structure. They are useful for rendering or provisional interpretation, but they are not facts unless crystallized back into Gojo structure.

Navigating With New Information

When new information appears, the reader should navigate from the affected local site instead of rescanning as a flat classifier:

  1. Re-read the touched relation, carrier, location, or unit shape.
  2. Update the local read node and any evidence it carries.
  3. Follow shared carriers, TickRef sites, parent relations, and attachment edges to the next affected reads.
  4. Preserve unresolved or incompatible evidence as ambiguity, residue, or tension-like read state.
  5. Let consumers render, solve, export, or condition AI from the current read graph at their requested resolution.

This makes discovery incremental. A point can become a segment endpoint, then a partition, then a branch site, without the renderer needing to ask every possible shape question again.

The first executable surface exposes this as:

GraphicReadGraph.Bands
  non-empty ordered read bands, currently primitive -> incidence -> control

GraphicReadGraph.NavigateFrom(changed, radius)
  local nodes around a changed relation, carrier, location, or TickRef

GraphicReadGraph.AffectedReadsFrom(changed, radius)
  reads carried by that local neighborhood

GraphicReadGraph.RefreshFrom(changed, radius)
  a rebuilt read graph plus previous/current affected neighborhoods

This is still explicit refresh rather than live eventing. It gives consumers a bounded neighborhood to reconsider when a shared site moves or new structure is attached, while the canonical source remains the relation graph.

Direction For GojoDraw

GojoDraw should eventually consume this read graph rather than running its own flat recognizers. Rendering then becomes a boundary lens:

GojoCAD structure
  -> derived read graph
  -> render recognized reads
  -> sample or draw partial/tension-like detail when exact detail is absent

Recognized structure should render as present. Missing radius, period, orientation, style, or sampled points should produce partial, sampled, or unresolved visualization instead of a failed draw branch.
