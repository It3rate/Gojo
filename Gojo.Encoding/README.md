# Gojo.Encoding

`Gojo.Encoding` is the experimental encoding layer for Gojo structures and
concept addresses.

It does not own Gojo meaning. Meaning still lives in connected Gojo carriers,
locations, relations, unit shapes, residue, tension, reads, and timelines. This
project builds small relation-shaped surfaces that can later be saved, read,
merged, generated by models, or lowered into compact integer packet formats.

The important bet is that an encoded concept should be more like a traversable
piece of Gojo structure than a random symbol. A name such as `speed` may remain
useful for people and tools, but the address for motion speed should also carry
some visible provenance toward distance, time, motion, rate, and context. The
same word can still mean a stimulant, a software optimization, or a cultural
idea. The lexical surface is not the whole concept.

## Project Boundary

`Gojo.Encoding` is separate from `Gojo/Core` on purpose.

Core should remain the kernel: carriers, relations, unit shapes, settlement,
tension, and reads. The encoding layer is a higher-level experiment over those
pieces. It can discover useful surfaces, fail, split, merge, and rename things
without forcing the kernel to adopt a premature file format or concept
catalog.

The boundary is porous in the useful direction:

- If an encoding surface is only a convenience for saving, loading, debugging,
  or machine learning, it should stay here.
- If an encoding surface reveals a missing numeric or structural primitive,
  the kernel may eventually need a smaller Gojo-native capability.
- If a read produced by this project becomes stable enough to be reused as
  structure, it should remain ordinary Gojo structure rather than becoming a
  code-owned snapshot.

## Current Footholds

The first implementation is intentionally tiny.

- `EncodedTextSurface` stores text as ordered Unicode scalar values in Gojo
  relation structure. It also exposes UTF-8 integer helpers for compact packet
  layers.
- `ConceptHintSurface` stores tiny query hints as carrier positions over small
  numeric bases. Packed query tokens are derived reads over those positions,
  not the source of hint meaning.
- `ConceptSeedSurface` packages readable text, a hint signature, optional opened
  Gojo structure, and residue/tension. It is read by field shape rather than by
  a marker tag.
- `ConceptAddressSurface` builds variable-length semantic addresses from atoms,
  compound parts, context, and residue/tension.

The split underneath those helpers is:

```text
local packet id
  stable reference inside one file or bundle

semantic address
  variable-length Gojo structure with provenance-like concept hints

debug lexical surface
  human-readable text, internationalized, useful for inspection and tools

learned vector
  optional derived read, not the source of meaning
```

The packet id may be a small integer. The semantic address should not be only a
small integer. It should be inspectable enough that a model, a merge tool, or a
human can ask why one address was chosen and what lower-level ideas it is leaning
on.

## Integer Encoding Direction

The durable encoding should be integer-first.

No concept in the persistent format should require a floating point value to be
read. If a value looks like a float at a user boundary, the encoded form should
prefer one of these:

- integer ticks against a known unit shape or basis
- numerator and denominator
- integer mantissa plus integer scale
- a resolution ladder
- a measured span with selected partition
- a residue-bearing read when precision is missing or incompatible

This matches the larger Gojo direction: resolution is part of the read. A
coarse value is not a failed fine value. It is a valid read at the available
resolution, with lower detail absent, unresolved, or represented as tension.

## Text And International Characters

Debuggability matters. Names, labels, source comments, documentation titles, and
language surfaces should be preserved rather than stripped away.

The text strategy has two layers:

```text
Gojo text surface
  ordered Unicode scalar points as relation structure

packet text surface
  UTF-8 bytes as integer values for compact binary-oriented storage
```

This means the binary format should be easy for a tool to scan for strings even
when it does not understand the full Gojo graph yet. It also means names are not
limited to English or ASCII. International language surfaces are first-class
debug and documentation evidence.

Text is still not the source of concept identity. A text label is a readable
surface attached to an address, source document, read witness, or residue. The
structure around the text says what role that text is playing.

## Concept Addresses

A concept address is a small Gojo structure that can be used anywhere an encoded
node needs to say what kind of idea it is participating in.

The current surface supports:

```text
atom
  lexical name
  residue or tension

compound
  lexical name
  part frame
  context frame
  residue or tension
```

For example:

```text
distance
time
motion
vehicle
speed:motion-rate(distance,time;context=motion,vehicle)
```

That is not meant to be a final ontology. It is a readable foothold. The useful
property is that `speed` can be decomposed through local structure, and a
different `speed` can decompose differently:

```text
speed(distance,time;context=motion)
speed(stimulant;context=slang)
speed(computation,time;context=software)
```

The shared word is evidence. The address structure decides what that evidence is
being used for in this local bundle.

### Cross-Context Echoes

Many seeds are not isolated to one category. More importantly, many different
contexts reuse the same smaller primitive tendencies.

This does not mean a temporal word should be treated as a spatial word. It means
that temporal order, spatial order, logical order, social order, and procedural
order can all carry a tiny shared hint: "this talks about order relative to a
reference."

For example, `in front of` and `before` are different local concepts, but they
both often use:

```text
reference object
  treated like local zero

ordered side
  one side of that reference rather than the other

context
  temporal, spatial, procedural, logical, social, or another local basis
```

The side may be only a bit or a very small signed value: before/after,
front/back, upstream/downstream, prior/later, above/below in rank. The local
meaning still comes from the surrounding structure.

The same pattern appears outside position words. `Sharp` can be literal
sharpness, but related hints show up in phrases such as "you have a point",
"a sharp distinction", "a cutting remark", or "cut in line." Those uses are not
all the same concept. They may simply echo smaller hints such as:

```text
boundary
edge
narrow focus
high contrast
separation
intrusion
forceful transition
```

The hint layer should capture those faint echoes without expanding them into a
full parse. A model or database can use the hints to find analogies, candidate
translations, or low-resolution neighbors. It should not conclude that all
echoing concepts are interchangeable.

So the address should be able to say:

```text
this local use is before-as-time
hint: order
hint: reference-relative
hint: negative-or-prior side
```

or:

```text
this local use is cut-in-line
hint: order
hint: boundary crossing
hint: intrusion
hint: social/procedural context
```

The hints are deliberately small. They are low-resolution handles, not the
complete concept.

### Concept Address Hint Encoding

The conceptual address should have a tiny scan surface and an optional opened
structure.

The current preferred shape is:

```text
concept address
  lexical text surface or text reference
  compact hint signature
  optional local sense discriminator
  optional opened Gojo structure
  residue or tension
```

The compact hint signature is the part meant for quick lookup. It should be much
smaller than a parsed concept object. A hint may be a single bit, a tiny signed
value, or a small packed token.

```text
primitive hint
  primitive axis
  optional polarity or side
  optional strength
```

Examples of primitive axes:

```text
order
boundary
containment
support
source
target
path
opposition
similarity
separation
intensity
rate
attention
agency
uncertainty
```

Examples of tiny modifiers:

```text
polarity
  negative / zero / positive

side
  before / at / after
  inside / boundary / outside
  source / path / target
  lower / equal / higher

strength
  weak / ordinary / strong

context lane
  spatial / temporal / logical / social / procedural / perceptual / domain-local
```

Those modifiers do not need to be full integers in the conceptual sense. Many
can be bit fields. The Gojo relation surface can still expose the same hints as
structure when opened, but the fast query form should stay compact.

Example:

```text
before
  axis: order
  side: negative/prior relative to reference
  context: temporal

in-front-of
  axis: order
  side: forward relative to reference orientation
  context: spatial

cut-in-line
  axis: order
  axis: boundary
  side: intrusive crossing
  context: social/procedural
```

The exact axes and bit placements are not frozen. The important decision is that
the hint is not the whole address and not a full semantic parse. It is a compact
surface that makes near concepts easier to find.

The first executable foothold is `ConceptHintSurface`. It represents a hint as
Gojo relation structure:

```text
hint
  axis point on primitive-axis carrier
  side/polarity point on signed side carrier
  context point on context carrier
  strength point on strength carrier
  optional opened Gojo structure
  residue or tension
```

The bases are also Gojo structures:

```text
axis basis
  segment from 0 to the current primitive-axis partition count

side basis
  signed segment around the reference point

context basis
  segment over context lanes

strength basis
  segment over weak/ordinary/strong read support
```

This keeps the hint compatible with ordinary Gojo reads. A prior/before hint is
not only a symbolic flag; its side is literally a negative position on the side
carrier. A spatial/front hint can use the same order axis with a different
context lane. A sharpness hint can carry a compact edge axis while opening into
a relation structure that contains a vertex and two rays.

The packed token is only a query read:

```text
hint relation
  -> packed UInt32 or UInt64 query token
```

The token exists so a database can scan quickly. If the token and opened
structure disagree, the disagreement should be preserved as residue/tension
rather than hidden.

### Concept Seed Surface

`ConceptSeedSurface` is the first small concept-shaped package over the hint
surface.

```text
concept seed
  readable text
  compact hint signature
  optional opened Gojo structure
  residue or tension
```

It deliberately does not use a marker string. A reader recognizes it by field
shape:

```text
text surface
hint signature
opened structure
residue/tension
```

This lets simple seeds stay small while preserving a route into richer
structure. For example:

```text
before
  hint: order axis, negative side, temporal context

in-front-of
  hint: order axis, negative/front side, spatial context

sharp
  hint: edge axis, reference side, perceptual context
  opened structure: vertex with two diverging rays
```

The point is not that `before` and `in-front-of` are the same. The point is that
they can share a small order/reference hint while keeping their local sense and
opened structures separate.

Seed residue remains visible. A phrase such as `cutting-remark` may carry a weak
edge hint in a social context while preserving residue that says the metaphor is
not literally a cutting edge.

#### How Many Values?

For a useful first implementation:

```text
tiny seed hint
  1 to 4 bytes, or a few bit flags

simple common concept
  2 to 8 compact hint tokens

polysemous common word
  several small sense hints, usually 2 to 8 tokens each

domain concept with provenance
  compact hints plus an optional opened structure

large documentary concept
  query through compact hints; inspect opened structure only when needed
```

In other words, the scan surface should often fit in a few bytes, and commonly
fit inside one or two machine words. If we need dozens of integers to understand
the hint, we have probably stopped making a hint and started encoding a parsed
object.

```text
query signature
  1 to 8 packed hint tokens
```

The opened Gojo structure can be larger. That is where provenance, role frames,
residue, examples, documentation links, and learned reads can live. The query
signature should remain small enough that a database can index it cheaply.

#### Byte Stream Or Something Else?

Use compact tokens for hints, and lower those tokens to bytes for storage.

```text
canonical conceptual form
  Gojo relation structure

hint scan form
  one or more packed integers or bitsets

database query form
  indexed packed hint tokens

binary packet form
  bytes containing those packed tokens
```

Bytes are good for files. Packed integers or bitsets are better for scanning and
database indexing. The Gojo structure is better for inspection and manipulation.
They should be different views over the same address, not competing meanings.

One practical packed token shape:

```text
UInt16 or UInt32 hint token
  primitive axis id
  small context lane
  side/polarity bits
  strength bits
```

Another practical shape is a fixed bitset for the most common primitive axes,
plus a few small side/polarity fields. That may be enough for a surprising
amount of lookup work:

```text
axis bitset
  order + reference-relative + boundary + intrusion

modifier bits
  negative/prior side
  social/procedural context
```

The full opened structure keeps the richer roles, text, residue, examples, and
provenance. The hint only gets us into the right neighborhood.

#### Learned Neighborhoods

Training should help tune these hints. The goal is not necessarily to copy a
word2vec architecture or store large learned vectors in every address.

The useful idea is that many examples can adjust which primitive hints belong
near each other and how strongly they should be expressed. A trained process
might discover that `sharp`, `point`, `cut`, `edge`, `precise`, and
`interruption` share a faint primitive neighborhood even when their surface
contexts differ.

The encoded result can stay small:

```text
learned hint adjustment
  add weak edge hint
  strengthen boundary hint
  weaken literal-cut hint in social context
```

A trained model can still use embeddings internally. The persistent conceptual
address should store the small hint result, plus enough residue/provenance to
explain that the hint is learned or uncertain.

If a learned codebook is useful later, it should be optional:

```text
hand-readable hint bits
  always available

optional learned code
  compact neighborhood id or adjustment id

residue
  where learned hint and local structure disagree
```

That keeps the training-derived hints useful without making them opaque or
oversized.

## Partial Files And Missing Structure

The format should remain viable when only part of it is present.

A missing referenced node is not automatically an error and should not collapse
to a generic `unknown`. It can be read as one of several lower-resolution states:

- aspirational reference
- missing source evidence
- unresolved correspondence
- future structure promised by a read
- merge residue
- damaged packet residue

That lets half a file remain useful. A PCB footprint can still say "I expect a
net address here" even if the net frame is missing. A concept can still say "I
think I am made from distance and time" even if the local bundle does not define
the preferred distance or time addresses.

## Merging Independent Bundles

Two independent files should be mergeable without requiring either file to be
the parent of the other.

The first merge behavior should be conservative:

```text
bundle A structure
bundle B structure
correspondence candidates
merge residue
read witnesses over what matched and what did not
```

If both bundles define `speed`, the merge should not immediately pick one. It
should preserve both addresses, expose any shared parts, and leave tension where
the same lexical surface points to different structures.

This is also how strange but viable combinations should work. A compound such as
`baseball-on-horses` may not be useful, but it can still be structurally viable:
baseball and horse-riding can participate in one unsettled compound with residue
that says the composition is not yet a stable concept.

## Reads As Encoded Structure

A read should be saveable as structure.

When a model, tool, or human asks "what is this?", the answer should be more than
a string. A useful read can contain:

```text
selected source
read surface or basis
result
residue or tension
provenance
timeline or refinement history
```

Those reads may start as derived inspection output. If they become important,
they should be able to become encoded structure in their own right. That is the
bridge between "a tool read this bundle" and "this bundle now contains evidence
that future tools and models can read."

## Machine Learning Requirements

The format should be usable by models in at least three modes.

### Sequence Generation

A model should be able to generate a valid stream of integer packets. That
stream may be incomplete or low-resolution, but it should decode into traversable
structure with visible residue rather than crashing into one invalid state.

### Graph Or Relation Reading

A model should be able to read the bundle as nodes and relation-shaped frames.
Cross-links, missing links, circular links, and ladder rungs are expected rather
than exceptional.

### Embedding-Like Concept Work

A model should be able to derive vectors or other learned summaries from
concept addresses, read witnesses, and local neighborhoods. Those vectors may be
stored as derived reads, but they should not replace the Gojo structure that
explains what the concept was built from.

This suggests a two-layer identity strategy:

```text
stable packet identity
  local integer id, useful for references and storage

semantic identity
  Gojo address structure, useful for interpretation and generation
```

The local id can be short and arbitrary inside one bundle. The semantic identity
should be longer, extensible, and structurally meaningful.

## Primitive Concept Seeds

This project will eventually need reusable concept seeds. They should be
general enough to support language, perception, science, design, ECAD, graphics,
and other domains without forcing every domain into a single taxonomy.

The first seed set should be treated as provisional structure, not a closed
dictionary. A good primitive is one that many higher concepts can point through
without pretending that all meanings reduce cleanly to one root.

interior
  participation read as inside, contained, filled, or protected by a boundary

exterior
  participation read as outside, surrounding, excluded, or exposed beyond a boundary

  a participating subset, component, fragment, or selected region

whole
  a bounded or settled frame that parts can participate in

## Language And Provenance

Words should be treated as language evidence attached to concept structure.

A word often compresses many lower concepts. Usually people do not think about
those lower ideas while using the word. That compression is good. The encoding
only needs to preserve enough provenance that a model or read can reopen the
compression when useful.

Examples:

```text
fast
  may point toward rate, short duration, high motion, high change, high response

speed
  may point toward motion rate, computation rate, stimulant, urgency, or style

hot
  may point toward temperature, danger, popularity, attractiveness, or recency

red
  may point toward light/color, warning, political context, heat, blood, or stop

near
  may point toward distance, probability, similarity, time, or relationship
```

This is why the address needs parts, context, and residue. The same lexical
surface can be locally precise while still preserving weaker associations to
other meanings.

## Domain Layers

Domain-specific concept libraries should be separate layers over the general
encoding seeds.

Examples:

```text
Gojo.Encoding
  text, concept address, primitive seeds, packet grammar

Gojo.Encoding.Ecad or GojoCAD encoding surfaces
  net, pad, footprint, schematic symbol, pin function, trace, clearance,
  copper side, drill, design rule, manufacturability

Gojo.Encoding.Graphics or GojoDraw surfaces
  contour, fill, stroke, color style, composition, layer, frame, camera

Gojo.Encoding.Language
  word surface, morphology, translation, sentence role, document provenance
```

The lower layer should not know every ECAD or graphics concept. It should make
it possible for those concepts to be encoded in a way that still traces back
through general ideas such as boundary, contact, flow, orientation, resolution,
support, and constraint.

## Physical Bundle Sketch

The physical format is not implemented yet, but the current direction is a
bundle made from integer records.

One possible packet sketch:

```text
bundle header
  magic text surface
  encoding version
  root packet id

string records
  packet id
  UTF-8 integer bytes

node records
  packet id
  local kind address
  optional source span

relation records
  packet id
  root packet id
  ordered element refs

address records
  packet id
  concept address relation

read records
  packet id
  selected source refs
  read surface refs
  result refs
  residue refs
  provenance refs

external evidence records
  packet id
  URI or path text
  media/content hash integers
  attachment target refs
  residue or unavailable evidence
```

The records should be readable in a streaming way. A tool should be able to pull
out strings, local ids, and rough relation frames before resolving the complete
structure.

## Repository-Like History

The larger format may want something like a repository, but not exactly Git.

Useful Git-like properties:

- stable blobs or packets
- content-addressable evidence
- cheap branching
- visible history
- merge records
- ability to compare versions

Gojo-specific differences:

- partial reads should be first-class, not merely diffs between snapshots
- old versions can remain active structure for new reads
- a merge can preserve contradiction as tension instead of choosing a winner
- read witnesses and model-generated interpretations can be committed as
  structure
- unresolved references are potential structure, not only broken links

This suggests a bundle history where each step may contain both new structure
and reads over previous structure.

## What Not To Freeze Yet

Several decisions should remain loose until there is more code and sample data.

- The exact binary packet grammar.
- Whether concept seed addresses are generated by hand-authored fixtures,
  learned from corpora, or both.
- How large semantic addresses should become before they are factored into
  reusable subaddresses.
- How much of a learned embedding belongs in the bundle versus in an external
  model index.
- Whether a string table should be mandatory or only a compression/readability
  layer.
- How aggressive merge correspondence should be when addresses partially match.
